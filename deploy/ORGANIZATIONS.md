# Одна «Череда», отдельные организации

Пользователь один раз вводит код организации, затем свой логин и пароль.
Основная организация: **ООО «Технодор СК»**, код `tehnodor-sk`.
Код — публичный адрес, не пароль. При смене организации выполняется выход.
Приложение разделяет сессии, настройки и кэш по серверу, организации и пользователю.
После обновления со старой версии потребуется выбрать код и войти заново.

Каждой организации выделяются отдельные API, база PostgreSQL, Docker volume,
секреты JWT/bootstrap и папка резервных копий. Общими остаются HTTPS-шлюз Caddy
и исходный код. Роль `super_admin` управляет только своей организацией.
Организации создаёт оператор сервера, не администратор внутри приложения.

## Обновление основной установки

Новый клиент требует нового сервера: `/o/tehnodor-sk/api/v1/organization`.
Не раздавайте новый APK до обновления API и шлюза. Старый `/api/v1/` оставлен
для совместимости, но старые access-токены без аудитории больше не принимаются.
Новый вход или обновление refresh-токена выдаёт токен с нужной аудиторией.

Перед обновлением: остановить API, сделать приватный `pg_dump -Fc`, восстановить
копию в отдельную тестовую БД, сравнить контрольные суммы и проверить миграцию.
Сохранить прежние образ API, Compose/Caddyfile и `.env`. В `.env` добавить
`ORGANIZATION_CODE=tehnodor-sk` и `ORGANIZATION_NAME=ООО «Технодор СК»`.
Не менять существующие пароль БД, JWT_SECRET и BOOTSTRAP_TOKEN.

Новая Compose-конфигурация создаёт сеть `chereda_gateway`, соединяя с ней Caddy
и API. Базы и backup-контейнеры остаются в собственных сетях. Для основной API
используется уникальный DNS-псевдоним `org-tehnodor-sk-api`: общий псевдоним `api`
нельзя использовать в шлюзе — несколько Compose-проектов имеют сервис `api`.
Каталог `deploy/organizations/` должен существовать перед запуском Caddy.
Сначала проверить `docker compose config --quiet`, затем поднять обновлённые API
и Caddy; PostgreSQL volume не пересоздавать. Не использовать `down -v`.

## Добавление организации (оператор, Linux-сервер)

Команды выполняются в `deploy/`. Пример ниже использует вымышленный код `company-b`.
Запускать только после обновления основной установки и создания gateway-сети.

```sh
python3 prepare_organization.py company-b 'ООО «Пример»'
docker compose -p chereda-company-b --env-file organizations/company-b.env -f compose.organization.yaml config --quiet
docker compose -p chereda-company-b --env-file organizations/company-b.env -f compose.organization.yaml up -d --build
docker compose -p chereda-company-b --env-file organizations/company-b.env -f compose.organization.yaml ps
docker compose -p chereda-company-b --env-file organizations/company-b.env -f compose.organization.yaml exec api python -m app.provision_admin --login admin
```

Пароль администратора вводится интерактивно без отображения. Скрипт не меняет
пароли существующих пользователей и не выводит токены. Файлы `.env` приватные,
имеют права 0600 и игнорируются Git; никогда не отправляйте их пользователям.
Сгенерированные конфигурации нельзя перезаписывать и нельзя копировать секреты
или базу другой организации. База запоминает свой код и отказывает в запуске
при попытке подключить её к другому коду (даже до миграции).

После здорового состояния API проверить из контейнера `/api/v1/organization`
(ожидаются код `company-b`, корректное название и заголовок X-Organization-Code).
Далее опубликовать только подготовленный маршрут и проверить конфигурацию:

```sh
mv -n organizations/company-b.pending organizations/company-b.caddy
docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
```

Если validate завершился ошибкой, не делать reload: вернуть новый файл в `.pending`
и исправить его. Проверить по HTTPS `/o/company-b/api/v1/organization`, затем вход
и пустой список сотрудников. Неизвестный `/o/unknown-code/api/v1/organization`
должен вернуть 404; чужие access/refresh-токены — 401, неверный заголовок организации — 404.
После этого передать сотрудникам код организации и личные учётные данные отдельно.

Резервные копии новой организации находятся в `deploy/backups/company-b/`.
Проверять их восстановление отдельно. Для отката использовать образ и БД именно
этой организации; нельзя подменять организационный код в скопированной базе.
Оператор VPS имеет доступ ко всем контейнерам: это изоляция организаций в приложении,
а не отдельные физические серверы. Лимиты ресурсов и хранение копий вне VPS задаются
при подключении реальных дополнительных организаций.

## Безопасное сокращение состава

`backend/scripts/retain_department.py` — операторская разовая операция, а не миграция
при запуске приложения. По умолчанию формирует план. Применение требует явных UUID
сохраняемых сотрудников, количества активных карточек и fingerprint этого плана.
Обязательны восстановленная резервная копия и остановка API. Скрипт архивирует
прочие карточки, отключает связанные рабочие логины, оставляет администраторов,
сохраняет историю и часы. При неожиданных привязках руководителей или изменившемся
составе отказывается работать. Все изменения в одной транзакции.
