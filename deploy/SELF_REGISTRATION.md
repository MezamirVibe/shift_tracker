# Самостоятельная регистрация организаций — 1.4

На первом экране и под входом есть «Создать организацию». Владелец задаёт название,
свой логин и пароль. Одобрение оператора не требуется. Код организации случайный:
клиент не может выбрать существующую организацию или присвоить её себе.

Публичный API только записывает заявку. Отдельный host-worker создаёт из общего
проверенного образа отдельные PostgreSQL/API/backup-контейнеры, секреты и пустую базу,
добавляет владельца и лишь затем публикует маршрут Caddy. Docker socket в публичный
API не передаётся. Ни демонстрационные сотрудники, ни структура не копируются.

В `.env` основной установки включить `PUBLIC_REGISTRATION=true`, затем пересоздать
основной API. В остальных организациях параметр остаётся выключенным. Установить
`chereda-registration.service` и `.timer` в `/etc/systemd/system/`, выполнить
`systemctl daemon-reload` и `systemctl enable --now chereda-registration.timer`.
Worker работает от пользователя deploy, у которого уже есть доступ к Docker.

Если установка системных units недоступна, достаточно пользовательского cron deploy:
`* * * * * /usr/bin/timeout 480 /usr/bin/python3 /opt/shift_tracker/deploy/registration_worker.py >> /opt/shift_tracker/deploy/registration-worker.log 2>&1`.
Существующие задания cron нужно сохранить. Worker сам блокирует одновременный запуск.

Образ новых API: `CHEREDA_API_IMAGE` из env организации, по умолчанию `deploy-api:latest`.
Таблицы заявок находятся только в управляющей базе. Секрет для проверки состояния
сохраняется на устройстве в защищённом хранилище; пароль туда не записывается.
В базе заявки хранится только Argon2-хеш пароля, после завершения он очищается.
Проверка статуса требует секрет заявки; он не передаётся в URL и access-логи.

Защита ресурсов: не более двух заявок с одного подключения в сутки, не более десяти
организаций по умолчанию. Значения `REGISTRATION_PER_IP_DAY` и
`REGISTRATION_MAX_ORGANIZATIONS` меняет оператор при увеличении мощности сервера.
Это лимит ёмкости, не ручное одобрение. Не поднимать без оценки памяти/диска.
Контейнеры новых организаций имеют отдельные ограничения памяти и процессов.

После сбоя заявка возобновляется через 10 минут, максимум три попытки. Конфигурации
и базы при сбое автоматически не удаляются; чужая конфигурация не перезаписывается.
Не включать это на нескольких управляющих API с независимыми базами/worker одновременно.
Для массового публичного запуска дополнительно нужны подтверждение контакта/антибот
и политика хранения данных; здесь реализован ограниченный самостоятельный запуск.

## Удаление и структура

Удаление сотрудника стало окончательным: карточка, её история, часы и закрытия удаляются
одной транзакцией. Нужен явный параметр `permanent=true`; старый клиент получит просьбу
обновиться вместо неожиданного удаления истории. Пользователь видит последствия в
подтверждении. Отключение связанного входа отдельно подтверждает суперадминистратор;
себя или другого суперадминистратора отключить этим способом нельзя.

Удаление группы/подразделения с `detach_members=true` оставляет людей без соответствующей
привязки, не удаляет часы и сохраняет старые названия в истории. Действующая учётная
запись с областью доступа по удаляемой структуре блокирует действие: её нужно явно
перепривязать или отключить в «Пользователях». Права доступа автоматически не расширяются.
